## 00｜开场：先把训练环境做出来

【画面】人机对局盒子里的战斗片段，切到没有游戏窗口的 Linux 对局进度，再切到“观察、行动、推进、学习”四个词。

如果想训练一个皇室战争 AI，第一步不一定是把模型做得很大。

你先得给它一个可靠的训练环境：它要知道场上发生了什么，能提交动作，能看到动作之后的变化，还要能重复打很多很多局。

这个项目做的，就是把这些环节接起来。

今天主要讲三件事：怎么把 libg.so 里的战斗能力包装成接口，怎么理解和验证游戏里的指针链，以及怎么在 Linux 上运行多场对局，让采集和学习真正连起来。

最后也会展示实际压测结果，以及哪些听起来很先进的优化，最后并没有被采用。

## 01｜libg.so 是什么，我们究竟复用了什么

【画面】共享库 → 原生战斗逻辑 → 游戏资源；旁边标注“不是 Linux 操作系统内核”。

这里说的“游戏内核”，不是操作系统内核，而是承载游戏原生逻辑的动态库。

libg.so 也不只有战斗功能。完整客户端里还有初始化、资源、显示和其他依赖。我们的工作，是把运行战斗所需的那条路径接出来。

也就是说，移动、攻击、伤害、圣水、单位生成这些战斗演算，仍然交给绑定版本的原生逻辑。Python 主要负责发送命令、整理观察和运行模型，不是在 Python 里重新写一套皇室战争规则。

但这不意味着整个客户端完全不需要适配。无界面启动仍然要处理宿主生命周期、资源加载和显示依赖。我们做了这些适配，同时保留战斗逻辑和版本检查。

版本尤其重要。同样叫 libg.so，不同版本、不同 CPU 架构，内部布局和函数位置都可能不同。所以启动前不只看文件名，还会核对版本、ABI 和文件哈希。不能只改个版本号，就把旧地址继续用下去。

## 02｜指针链：从一串地址，走到一场对局

【画面】概念图：模块基址 → 全局指针槽 → manager → context/state → battle → 玩家与实体。逐个高亮“取地址”和“读取指针”。

指针链可以理解成一张对象之间的路线图。

游戏运行时，会有管理当前状态的对象、代表一场战斗的对象，以及玩家、单位和实体集合。它们不一定连续放在内存里，而是通过指针相互引用。

第一步是找到当前进程里 libg 的加载基址。因为地址随机化，同一个库下次启动时，绝对地址可能变了。

然后用已经验证的相对位置，找到全局指针所在的槽位，读出管理对象的地址，再沿着对象字段，一层层走到战斗和实体集合。

注意，这不是把几个偏移直接加在一起。每经过一个指针字段，都要先读出它指向哪里，再继续访问下一层。

这里要区分两种位置：一种是函数在模块里的相对地址，另一种是字段在某个对象内部的偏移。它们不是同一个概念。

这些位置怎么确认？可以结合反汇编、调用关系、引用关系和运行时状态做交叉验证。找到一个“看起来像圣水”的数字，只能算候选，不能就此认定整条链正确。

我们会观察：暂停回放时 Tick 是否停住，播放时是否继续增长，单位坐标是否变化，下牌后手牌是否轮转、圣水是否下降。再看退出和重新开局以后，对象是否重新绑定。

还有个很容易踩的坑：对局结束了，旧对象可能依然能读。因此，“指针非空”不等于“游戏正在进行”。需要结合时钟、场景、己方身份和终局条件一起判断。

采样时也会在读取前后检查 Tick 和对象身份，减少把两个时刻拼成一帧的问题。不过，这种检查并不等于给整个游戏做了原子快照。

【字幕】图中的对象名字是工程职责命名；偏移只对已验证版本有效。

## 03｜两条路线：观察在线客户端，和驱动本地沙盒

【画面】左右分屏：MuMu 实时读取链；Linux/本地无头训练宿主。

这里有两套容易混淆的系统。

一套是 MuMu 里的实时接口。它观察正在运行的客户端，读取局面和己方信息，操作通过普通触摸发送。我们不是在这个路径里写游戏内存，也不是调用在线客户端的内部下牌函数。

另一套是本地无头训练沙盒。这个进程由我们自己创建和管理，所以可以通过 JNI 桥接层，调用经过版本绑定的原生战斗入口。

这两条路线的游戏版本和架构也不一样。本期 Linux 压测使用冻结的旧版 x86_64 运行时；MuMu 的 ARM64 实时适配是另一条链，不能把它的偏移直接套进 Linux 训练宿主。

在沙盒里，我们把内部能力包装成几个比较容易理解的接口。

reset 创建或重置对局；observe 读取局面；step 推进若干次原生更新；probe_grid 检查一张牌当前可以部署的位置；act 和 ability 分别处理普通下牌与主动技能。

训练时，还可以把双方动作、推进和下一帧观察合在一次请求里，减少来回通信。

提交下牌，也不是直接往地图上凭空塞一个单位。桥接层要找到玩家，确认卡组索引对应当前哪张手牌，再走原生选择和部署验证，构造、执行并释放命令，最后读取是否被接受的回执。

如果通信中断，不确定动作是否已经执行，就不能盲目重发。否则一次下牌可能变成两次操作，训练数据也会跟着失真。

## 04｜为什么 Linux 上不需要开一堆安卓模拟器

【画面】Linux 内核 → Android Bionic/ART 用户态 → Java 宿主 → JNI Bridge → libg.so。

早期环境可以在没有可见窗口的安卓模拟器里跑，但在云端扩大并发时，完整虚拟设备会带来额外成本。

Linux 路线保留的是游戏库需要的 Android 用户态依赖，比如 Bionic 动态链接器、ART、Java 类库、属性区和资源目录，再启动一个不依赖完整安卓系统服务的宿主。

因此，已验证的这条 x86_64 路线不需要启动 AVD，也不依赖 KVM。它仍然依赖 Android 兼容运行环境，并不是把 Android 的库随便丢给普通 Linux 程序就能直接运行。

初始化也不能只保留一段战斗函数。地图、卡牌表、资源、玩家和战斗状态之间有依赖。缺少某些资源时，程序可能看似启动了，但战斗实际上没有正确建立。

所以每次部署都要先确认：资源和版本匹配，对局可以创建，Tick 正常推进，塔和玩家状态正确，动作能得到有效回执，结束以后还能重置。

这一步解决的是“有没有一个可靠的训练场”，不是模型水平问题。

## 05｜一个进程四场对局，到底是怎么运行的

【画面】一个原生进程框内放 A/B/C/D 四个槽；一个执行标记依次移动。外层再展示多组进程并行。

当前实验里，一个原生进程可以驻留四个战斗对象。

但“四场同时驻留”，不等于四个线程同时进入同一份 libg。我们仍然保留一条原生执行通道，在四场对局之间交错推进。

每场对局都有自己的状态。切换槽位时，选择对应的战斗对象，保存和恢复适配层需要的对局信息。结束一局，就重置它，不影响其他槽位。

模型侧也必须隔离。A 局的历史出牌和 LSTM 记忆，不能带进 B 局。我们曾经在 CUDA Graph 实验里发现隐藏状态存储被不同玩家复用，验证器直接把它拦了下来。

四局的主要价值，是摊薄进程和运行环境开销，并把准备好的玩家视角合批送给 GPU。真正利用多核，则是在外层启动多组独立进程。

本期说的“12×4”，是十二组采集 worker、四十八场驻留对局。每组还配有策略进程；并不是整台机器只有十二个操作系统进程，也不是所有对局只使用一份 GPU 模型。

为了确认没有跨局污染，我们会用同一批种子比较动作轨迹、终局和观察字段，还会在其他对局仍然活跃时反复重置某一个槽位。

这种一致性是对已测试字段与场景的验证，不是对所有卡牌和所有内部状态的数学证明。

## 06｜模型看到什么，什么时候做决定

【画面】实体特征、空间网格、己方手牌、历史出牌 → 模型 → 等待/行动、卡牌、位置。

原生观察和模型输入之间，还隔着一层编码。

本期接入的模型约四百八十万参数，不是早期那版一亿七千七百万参数的专家。它使用实体与空间特征、历史出牌信息和 LSTM，再输出时机、动作类型、卡牌以及位置等结果。

环境为双方生成训练视角时，内部可以拿到很多信息，但策略输入不能因此偷看对手私有手牌和精确圣水。观察要先投影到当前玩家视角，再进入模型。

当前这版模型每四个原生 Tick 做一次决策。原生 Tick 是二十赫兹，所以在游戏时间里，相当于每二百毫秒判断一次，而不是每一 Tick 都调用模型。

判断一次，也不代表必须下牌。策略可以等待；选择行动后，还要结合当前手牌、费用、部署区域和技能可用性进行约束。

这里的二十赫兹描述的是游戏逻辑时间。无头环境不需要每一步都在现实中等待五十毫秒，而是尽快计算。这正是模拟训练可以加速的原因。

但我们不会通过把物理步长随意改大来提速，因为那会改变训练环境本身。

## 07｜数据和自博弈：从“双方在打”到“模型在学”

【画面】一条数据来源链；再展示“冻结策略采集”和“带参数更新的学习”两个不同标签。

数据这边，项目保留了来源、去重、版本检查、动作记录、原生复演和训练存储等模块。

特别要注意：把观察到的下牌时间和坐标重新输入原生引擎，并不自动等于恢复了真人当时的完整比赛。缺少原始随机种子、精确版本或状态锚点时，生成出来的局面要单独标记来源，不能当作已经证实的原始帧。

自博弈也有一个类似的区分：两个模型在环境里互相打，只能说明采集链路跑起来了。如果没有反向传播、参数更新和快照验证，模型并没有因为这些对局变强。

旧的 177M 路线，已经做过实际的 Critic 和 PPO 更新，但对手权重主要是冻结专家；完整的动态联赛对手池还没有接进主循环。

本轮针对新模型，做的是一个隔离的小规模闭环：采集器和学习器分成两个进程，用有上限的队列交接短数据段，不必等整批比赛全部打完才开始学习。

样本里除了观察、动作和奖励，还要保存真实的循环记忆起点、当时动作的概率、策略版本，以及这段数据到底是终局还是截断。否则 PPO 可能在用错误的条件重算概率。

这次审计复测收集了一千零二十四个学习方决策样本，完成八次输出头和价值头更新，并确认采集与学习存在实际时间重叠。

我们也专门检查了模型看到的不是固定开局：有新实体生成，有实体移动，实际输入网格出现了六百零七种不同状态。

为了让正在进行的对局继续使用兼容的记忆，这次冻结了主干和 LSTM，只更新输出头和价值头。原始专家文件和对手权重都没有被覆盖。

这说明小闭环接通了，不代表模型已经获得更高胜率，也不代表全网络和动态联赛已经完成。

## 08｜性能优化：先量清楚时间花在哪里

【画面】端到端计时分块，然后展示本轮 12×4 的三行对照表。

为了知道接下来应该改哪里，我们把 CPU 工作、GPU 实际计算和端到端等待分开计时。

一个常见误区，是把“模型前向函数耗时”全部算成 GPU 计算。实际里面还有 CPU 的准备、算子发射、数据传输和同步。

我们的样本里出现了大量很小的 GPU 内核调用。单个操作并不重，但反复发射和同步会积累开销。所以，一部分优化不是让 GPU 多做事，而是让 CPU 少重复解析，让 GPU 少接收细碎任务，让两边少来回等待。

先前一轮已经改进了历史窗口、同帧复用和宿主绑定。本轮继续比较固定缓冲区、CUDA Graph、编译以及传输接口。

在同一台机器、同一模型、同一批对局的十二乘四对照里，吞吐从大约六千二百二十八，提高到七千零二十九 tick 每秒，增加约百分之十二点九。对应对局的动作摘要和终局一致。

这里必须强调：这是四十八场驻留对局的聚合逻辑推进速度，计时包含推理和接口。不是单局七千帧，也不包含完整 PPO 学习耗时。

同时，显存从约八点二五 GiB 增到十点七六 GiB。这是有代价的优化。

也有没采用的方案。固定缓冲区单独用，收益不明显；当前编译配置算上初始化和新形状处理，比对照更慢；完整 JSON 再转二进制，也因为增加了一遍解析和对象构造而变慢。

紧凑观测的数据量倒是下降了约百分之五十八，但本机的吞吐基本没改善。这说明传输字节减少，不等于整个系统就一定更快。

所以最后留下来的，是测出有效收益、也通过一致性验证的组合，而不是把所有开关全部打开。

## 09｜现在做到哪，下一步缺什么

【画面】三个已验证项目与三个下一步目标，最后显示仓库地址。

到目前为止，项目已经具备原生战斗接口、独立的实时观察与操作路径，以及 Linux 上多局驻留、模型推理和性能验证的能力。新模型的异步输出头学习小闭环，也已经跑通。

但真正长时间训练一个强策略，还需要继续解决全网络更新、循环状态重建、对手池升级、独立评估和故障恢复。

尤其不能一直让模型刷同一个固定对手，然后只根据训练胜率判断自己越来越强。后续需要有近期模型、历史模型和不同打法的对手，并用独立评估决定哪些快照进入对手池。

这一期分享的是训练基础设施的进展。模型水平，要交给有清晰规则、可复现的对战评估来回答。

源码、实验结果和没有成功的尝试，我也整理到了仓库里。下一步，会在这座训练场上继续完善真正的自博弈训练。

【片尾字幕】原生接口与性能验证 ≠ 已超越人类；采集吞吐 ≠ 完整训练吞吐。

## 简介文案

这期分享 CR-Native-Core 的技术进展：libg.so 战斗接口、指针链定位与验证、Linux Bionic 无头运行、多局驻留，以及真实采集—学习小闭环。

本期 12×4 实验使用约 4.804M 参数的兼容发布模型；CUDA Graph 组合的聚合采集吞吐约 7,029 tick/s。该数值不是单局帧率，也不包含完整 PPO 训练开销。

主工程：[IMAX9D/cr-native-sandbox](https://github.com/IMAX9D/cr-native-sandbox)

Linux 运行层：[IMAX9D/cr-native-linux-bionic](https://github.com/IMAX9D/cr-native-linux-bionic)

技术与实测口径以仓库文档为准。视频不展示登录凭据、私有数据或未经验证的对战水平结论。
