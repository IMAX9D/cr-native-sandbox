# Linux 多并发架构：实现与云端实测

日期：2026-09-10 UTC。状态：本轮实现、短程对照与结果归档完成；B75 已在控制台确认关机，F59 保持关机。没有启动正式训练、改变模型权重或修改 R0。

后续本地工作另见 [列式推理路径验证](POLICY_COLUMNAR_PATH_20260910.zh-CN.md) 与 [worker 原生架构研究](WORKER_NATIVE_ARCHITECTURE_RESEARCH_20260910.zh-CN.md)。后续的本地代理基准不能混入本文云端成绩。

## 1. 结论

已经获得可靠的**宿主减负**，但不能宣称实现了大幅端到端训练提速，更没有达到每天 20 万场。

- 新原生观测返回路径省去 Java 对观测 JSON 的重新解析与整树序列化。单 worker 短测从 459.7 到 843.2 Tick/s；24 worker 下保持相近吞吐时，CPU 从 11.70 核降至 5.35 核。
- 多进程确实能突破单 Python 采集进程的吞吐平台。它是已有能力，本轮验证了配置和瓶颈，不能把它包装成新发明。
- 同为 4 个采集进程、24 个 worker，新返回路径的原生短测从 8014.6 到 8545.4 Tick/s，约 +6.6%；CPU 从 20.32 核降至 16.19 核。启用 ART JIT 后约 8551.0 Tick/s，CPU 进一步降至 10.46 核。
- 真实模型闭环试验中，最好的一组是快返回＋稀疏记忆传输，190.0 → 202.6 次**学习方决策/秒**，约 +6.6%。这是单次短测差异，不是经过重复试验确认的长期增益。
- 小分组调度、扩大合批等待窗口均出现负结果，不能默认启用。整条链路仍主要受小批量推理调度和数据组织开销限制，而非 CPU 核数或显存耗尽。

这不是 R0 的在线采集验收，也不是 160402002/ARM64 的 Linux 对局验收。旧专家模型的短测不能替代新架构、新版本的完整验收。

## 3. 先修复了冷部署缺陷

原发布包在新实例上不能直接启动，旧机器已有文件掩盖了这些缺陷：

1. `linker64`、`dalvikvm64` 缺少可执行位。
2. 发布包内的旧宿主 JAR 没有裸 ART 所需的 Android framework JNI 注册流程。
3. public-library 列表缺少宿主需要的 `libandroid_runtime.so` 等平台依赖。
4. 缺少 `asset-pack.apk`、`assets/assets.scdb`、`data/update/data_manifest.toml`，导致 GameMain 初始化时崩溃。

三个资源文件从已经校验的 432 备份提取，再逐文件核对 SHA-256。新旧性能路径都使用相同资源和同一个已验证 bridge：`ab52e3d7701f41ded657a2d2dd58f3328416d070cbea49019389e6eafcee2a66`。这些启动修复不计入性能增益。

诊断用的临时 C++ 修改没有保留在主工程，主工程 C++ 游戏步进、终局扫描与 libg 文件均未改变。独立诊断产物保存在实验输出目录。

新增 `CR-Native-Linux-Bionic/scripts/build_host_overlay_bundle.py` 可生成不覆盖原包的完整候选发布包；安装器增加资源缺失早期检查、可执行位恢复、启动身份记录和停止前的进程归属校验。

候选包位置：[runtime-fastjson-complete](D:/Deepseek/outputs/linux-architecture-prototype-20260910/runtime-fastjson-complete)。其 [BUNDLE-MANIFEST.json](D:/Deepseek/outputs/linux-architecture-prototype-20260910/runtime-fastjson-complete/BUNDLE-MANIFEST.json) 必须随包分发并显式传给安装/启动命令，不能继续使用旧发布清单。该重打包产物已构建和校验，尚未再租一台空白实例做第二次冷安装验收。

单进程约 2100 Tick/s 的平台没有因增加 worker 而消失。新路径释放了 CPU，却没有自动突破采集端瓶颈。

### 固定 24 Worker，多进程对照

| 采集进程 | 接口 / ART | 聚合稳定段 Tick/s | CPU 核数 | 45 秒计量期间自然终局 |
| ---: | --- | ---: | ---: | ---: |
| 1 | 旧接口 / interpreter | 2193.4 | 11.35 | 5 |
| 4 | 旧接口 / interpreter | 8014.6 | 20.32 | 50 |
| 4 | 新接口 / interpreter | 8545.4 | 16.19 | 55 |
| 4 | 新接口 / JIT | 8551.0 | 10.46 | 58 |

“聚合稳定段”是独立进程计量速率之和；原始记录另有包含启动、预热的整体墙钟速率，不能把两者混用。各进程使用互不重叠端口，所有计数来自校验过的原生 Tick；没有把请求数当 Tick。未观察到意外拒绝、RPC 合同失败或 OOM。

新旧接口还进行了同 seed、同动作规则的 400 次连续 transition 对照，累计每条路径 2000 Tick。去掉地址、代次和计时诊断字段后，解析后的动作和状态数值相等；JSON 数字表示可能是整数或浮点，因此原始文本摘要不同。该对照没有覆盖所有卡牌和所有终局路径。

## 5. 真正包含模型、采集、保存和校验的结果

以下全部是 4 个 CPU 采集进程、24 个原生 worker、同一个集中 GPU 服务，ART JIT。未进行 PPO 参数更新。

| 配置 | 决策数 | 总秒数 | 决策/秒 | GPU 平均利用率 | 记忆传输 MiB |
| --- | ---: | ---: | ---: | ---: | ---: |
| 旧接口，全量记忆，2ms 合批 | 16734 | 88.07 | 190.02 | 7.47% | 784.73 |
| 快接口，稀疏记忆，2ms 合批 | 15176 | 74.90 | 202.63 | 6.92% | 6.00 |
| 上述配置＋每小组 2 个 worker | 15804 | 85.90 | 183.97 | 7.17% | 6.19 |
| 快接口＋稀疏记忆＋dense 采样 | 15969 | 80.82 | 197.59 | 8.30% | 6.26 |
| 再加 CPU 预合批传入显卡 | 15853 | 85.65 | 185.08 | 7.52% | 6.26 |
| 上述配置改 8ms 合批等待 | 16473 | 106.02 | 155.38 | 5.19% | 6.52 |

判断：

- 稀疏记忆把每个决策都返回的 RNN 状态改为只在学习方序列锚点返回，传输降约 99.2%。模型仍然每次正常更新自己的记忆，不是跳过决策或删掉训练所需状态。
- 小组调度增加了调用碎片；8ms 等待也没有充分合成大批次，反而增加等待。两项保持默认关闭/原值。
- dense 采样与 CPU 预合批尚未证明端到端收益，保留显式试验开关，不默认推广。
- CPU 预合批在固定真实样本、单模型 16 行批次、带 cProfile 的短循环中，约 1640 → 2225 actor 行/秒。它不等于闭环成绩，也说明优化一个局部不能保证全局提速。
- 实际 GPU forward 通常只有约 6 行/模型。推理服务的 Python 调度、频繁的小批次调用，以及采集落盘校验仍值得优化。当前低 CPU/GPU 利用率不足以支持“换更多 CPU 就解决”或“177M 必须缩小”的判断。

## 6. 数据与正确性检查

从 `full-p4-collated` 的一个已校验分片抽样 267 帧：

- 浮点输入均有限；棋盘出现 260 种不同摘要。
- 动态卡牌实体数量为 0～16；塔楼始终存在，抽样中可见塔格数量为 6。
- 开局没有动态单位时，entity token 数可以是 0，这不等于空场；塔楼单独进入棋盘通道。
- 因此该样本不是固定开局/全零观测，但这不是对所有特征语义或策略防守能力的完整验收。

原接口仍保留，变更接口使用独立操作名；非幂等动作没有加入自动重试。稀疏记忆缺失、动作身份错位、非法层级、NaN/Inf、组间 worker 重复、分片不完整都会失败退出。

主工程针对本次改动运行 60 项选定测试，包含真实 Java 编译执行的字符串/Unicode/终局编码测试。Linux 仓库运行 18 项测试，17 项通过、1 项因本地 Windows 不支持 Linux rootfs 语义而跳过。新终止逻辑会核对 PID 命令行，不能对未知监听服务发送 shutdown 或误杀复用 PID。

## 7. 当前可采用和下一阶段应做的事

当前候选组合：完整部署包、ART JIT、快观测返回、多个独立 CPU 采集进程、一个 GPU 策略服务、仅传必要 RNN 锚点、有界请求队列。默认保留原决策与训练合同，不改奖励和模型来换吞吐。

下一阶段的架构重点应是：

1. 用固定真实轨迹做可重复的 CPU 编码、IPC、GPU forward、动作解码四段基准，采用 warmup 后重复测量。先明确当前小 batch 的损失，不再用单次对局用时选胜者。
2. CPU 采集进程只维护原生对局与编码状态；GPU 参数只驻留一次。把 Tensor/NumPy 对象树的逐请求 pickle 改成有版本、长度和身份校验的定长共享内存槽位；用有界 ready 队列控制背压。
3. GPU 以策略哈希＋形状桶调度，维护 per-worker/side 的 RNN 状态；先验证固定形状图执行，保留溢出回退和数值对照，再考虑 CUDA Graph/编译。不能只把等待时间拉长。
4. 把落盘整理和验证放到与下一批采样可重叠的流水线，但只有 CLOSED 且版本匹配的数据才能交给训练器，不能混合未完成策略版本。
5. 每进程多局驻留 K=2/4 是后续独立研究。当前一个 libg 进程仍只有一个战斗上下文；没有实现多局驻留或多线程同时调用同一内核，也没有完成 C++ 二进制观测协议。

本次没有启用 `torch.compile` 的云端性能试验；虽然服务入口已暴露已有编译能力，仍需单独做容量、数值和稳定性验证。R0 接入、正式学习更新、长期无人值守及每日至少多少场的承诺均不在本轮验收结果内。
