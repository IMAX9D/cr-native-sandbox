## 1. 实体指针批读：有减负，不能夸大吞吐收益

只将连续的实体指针表合并为一次有界读取，实体结构读取、扫描时点和终局逻辑不变。短读不使用部分缓冲，而回退至原逐项读取。默认仍是逐项模式，批读和计数均需显式开启。

- 实际 C++ 模板测试在 Windows 和云端 Linux/Bionic 都通过，覆盖逐项/批读、部分读取回退、边界、空表和快照行为。
- 两个固定种子分别运行717、908次决策，均达到自然终局；剔除内存地址、代次和计时诊断字段后，新旧路径的动作结果及状态逐条一致。
- 测量区间读取调用从1,284,412降至962,531，约少25.1%；读取字节同为109,407,881。
- 两种路径的测量区间均无新增读取失败；批读回退次数为0。初始化各自有一次失败探测，不能把它说成整个运行期间完全没有失败读取。

24 workers、4 collectors，5秒预热、45秒计量，关闭读取计数，交替执行三轮：

| 路径 | 三轮 Tick/秒 | 平均CPU核数 |
| --- | --- | ---: |
| 逐项读取 | 8464.8 / 8534.4 / 8483.0 | 10.47 |
| 指针批读 | 8463.9 / 8764.4 / 8548.4 | 9.88 |

批读平均CPU少5.6%，吞吐均值仅高1.2%，各次区间重叠，不能据此认定稳定的明显提速。既有“实体读取失败后忽略”的更广泛故障语义没有在本轮重写；本轮不是覆盖所有卡牌、技能和故障注入的全面验收。

## 2. 采集进程数：本轮已找到的明显瓶颈

不增加 worker、不改变 Tick，只将CPU采集进程从4个改为8个，每个负责的对局从6场变为3场。

| 24-worker配置 | Tick/秒 | 平均CPU核数 |
| --- | ---: | ---: |
| 4采集进程，逐项读取三轮均值 | 8494.0 | 10.47 |
| 8采集进程，逐项读取 | 16505.7 | 16.72 |
| 8采集进程，批读第1次 | 16174.0 | 16.77 |
| 8采集进程，批读第2次 | 16413.7 | 16.77 |

旧读取方式同样接近翻倍，说明主要收益来自采集端的多进程并行，而不是批读。不能再把“四个采集进程的吞吐上限”误称为libg或25核CPU的上限。所有这些计量均无异常拒牌。

两个冻结模型沿用已有内容：PPO policy19与专家参考157674。文件 SHA 分别为 `5dfb52e0b7284b33185d8bb484003662eefb30bc69eb082bd939b76fd35b480d`、`5016899ad11e2c98f4a68882f10a8fd25b88051096d44562ad38a56c30f476d4`，与已有备份一致。

真实GPU一致性测试使用128个中局观测、两个模型、32次连续循环状态更新。动态实体数量3～9；动作数值和RNN状态最大绝对差均为0。此项比较实际网络的两条输入路径，不是GPU kernel计时，也不是声称异步随机自博弈整局逐动作相同。

## 4. 共享只读库文件：已试，收益很小

只在隔离测试目录将24个`libg.so`映射到同一文件inode；文件内容和SHA不变，各进程的可变对局状态不共享。两个固定种子的717/908次决策对照再次通过，均自然终局。没有借此跳过Tick或复用别局状态。

在独立诊断负载下采样24个worker，而不将该带探针负载计入吞吐对照：

| 布局 | libg inode数 | PSS合计 | 私有脏页合计 | 线程数 |
| --- | ---: | ---: | ---: | ---: |
| 独立文件 | 24 | 5,880,907,776字节 | 4,652,085,248字节 | 1872 |
| 共享库文件 | 1 | 5,786,316,800字节 | 4,629,069,824字节 | 1872 |

PSS差异约90.2MiB、1.6%；私有堆也有波动，不能把全部差额都归因于库共享。共享布局的独立吞吐测量为16001 Tick/秒，未超过独立文件的16174/16414两轮结果，因此不将其列为主要提速路线。

每worker约78条线程，但本次两秒诊断采样中，CPU时间主要在`main`，其次`HeapTaskDaemon`；多数其他线程没有可计量CPU增量。没有线程生命周期缺失样本。线程数量多不代表都在争抢CPU，不应直接裁掉线程。

测试结束已停止所有测试worker，恢复隔离目录的24份独立库文件。原工程的worker和库文件始终未改变。

## 5. 尚未实现的部分和后续重点

- 每个worker仍是一局、一条libg执行lane。没有实现或测试K=2/4多局驻留，没有fork ART/CUDA，没有GPU重写物理引擎。
- 采集端即使接集中服务，仍会在CPU重复加载两份Actor，主要用于验证身份、读取配置和初始记忆信息。下一阶段可用经过内容校验的中央模型描述符消除这部分重复工作，而不能直接去掉身份验证。
- 完整采样还包含观测编码、请求构造、记录、分片写入/验证以及末尾慢对局。应分别优化常驻采集、有效合批和有界写入流水线；不是只增加worker或只追求GPU使用率。
- `inference_seconds`含输入准备、搬运、模型和动作采样，不等同于纯GPU计算时间；各collector时间会重叠，不能直接相加为墙钟时间。
